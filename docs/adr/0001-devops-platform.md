# ADR 0001: DevOps platform (version control, CI, release, CD)

- Status: Accepted
- Date: 2026-11-20
- Decider: Meer Hamza

## Decision

GICNEXT ships as **one Docker image per release**: built and tested in GitHub Actions,
then deployed to an Ubuntu server running the frappe_docker stack. Only free and
open-source tools are used, and the setup works within the **GitHub Free plan on a
private repository**.

```
feature branch ──PR──> main ──release-please PR──> tag vX.Y.Z + GitHub Release
     │                   │                                │
  pre-commit        CI: lint, security,           image.yml: build, smoke test,
  (local)           Frappe tests                  vuln scan, attach image to the release
                                                          │
                                                  deploy.yml: staging (automatic if configured)
                                                  production: deploy/local-deploy.sh (laptop)
```

## Context

- One person maintains this. Prefer boring, proven tools and as few moving parts as possible.
- The repository is **private** on GitHub Free. That rules out several GitHub features (see "Free-plan limits").
- The app is a Frappe v15 app (`gic_erp`) on ERPNext v15. Production runs several client
  sites on one bench (multi-tenant, one site per client).
- Production model: Docker (frappe_docker), chosen 2026-11-20 instead of a bare-metal bench.

## Decisions

### 1. Version control

| Topic | Decision |
|---|---|
| Branching | Trunk-based. `main` always releasable; short-lived `feat/…`, `fix/…`, `chore/…` branches; **squash merge** with the PR title as the commit message. |
| Commit format | Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:`, `ci:`, `build:`, `perf:`). Checked locally (pre-commit `commit-msg` hook) and on PR titles in CI. |
| Versioning | SemVer, driven by commits through **release-please**: `fix` → patch, `feat` → minor, `feat!` / `BREAKING CHANGE` → major. Version lives in `gic_erp/__init__.py`. Baseline `v0.5.0` = Milestones 1–5. |
| Changelog | `CHANGELOG.md`, generated by release-please. |
| Local gates | pre-commit: ruff (lint + format), prettier, eslint, JSON/YAML/TOML checks, gitleaks (secrets), shellcheck, hadolint, actionlint, large-file and private-key guards, Conventional Commit message check. |
| Ownership | `CODEOWNERS`, PR template with a checklist, issue forms for bugs and features. |
| Dependencies | Dependabot (free on private repos): GitHub Actions and the Docker images in the production compose file, weekly. Frappe/ERPNext versions are pinned in `deploy/versions.conf` and bumped by hand, since they need a test pass. |

### 2. CI (`.github/workflows/ci.yml`, on every PR and push to `main`)

| Job | What it does |
|---|---|
| lint | `pre-commit run --all-files`: the same hooks as on the laptop. |
| pr-title | PR title must be a Conventional Commit, because it becomes the squash commit. |
| security | gitleaks over the full git history; bandit (Python SAST). |
| tests | Real bench on the runner: pinned Frappe + ERPNext, MariaDB 10.6 and Redis containers, fresh site, `run-tests --app gic_erp`, and `bench build --app gic_erp`. A `before_tests` hook in `gic_erp` creates a Pakistani test company on a blank site. |

Every action is pinned to a full commit SHA, the default token is read-only, runs are
cancelled when a newer commit arrives, and every job has a timeout.

### 3. Release and image (`release-please.yml` → `image.yml`)

- `release-please` keeps a release PR open. Merging it creates the tag and the GitHub Release.
- Then `image.yml` builds the production image from `deploy/Containerfile`. It is adapted
  from frappe_docker's layered image, but the app source is copied in from the checked-out
  commit, so **no token goes into the build** and the image contains exactly the
  tested commit.
- Deploy rehearsal (`deploy/ci/rehearse-deploy.sh`): on the runner, the real
  `remote-deploy.sh` deploys the new image to an empty "server", a site with ERPNext and
  gic_erp is created and checked (`/api/method/ping`, GICNEXT login page, assets), the same
  release is deployed again over the live site (backup, migrate, health check), and finally
  a deliberately broken release is deployed and **must roll back automatically**.
- Vulnerability scan with **Grype**, report only (in the run summary and attached to the
  release). It does not block: gic_erp adds no Python or Node packages of its own, so every
  finding comes from the pinned upstream Frappe/ERPNext images and is fixed by bumping
  `deploy/versions.conf`.
- The image is saved as `gic-erp-<version>-amd64.tar.zst` and **attached to the GitHub
  Release** (free, so no paid registry is needed).

### 4. CD (`deploy.yml`)

- Target: any Ubuntu 22.04/24.04 server with Docker (`deploy/server/bootstrap.sh` sets it
  up: Docker, firewall, fail2ban, automatic security updates, a non-root deploy user).
- Production stack: `deploy/compose.yaml`, based on frappe_docker's compose (MIT). It runs
  Traefik with free Let's Encrypt SSL and one host rule per client site, MariaDB 10.6,
  Redis, gunicorn, the Socket.IO server, workers and scheduler, a migrator, and Ofelia
  backups every 6 hours.
- Deploy steps (`deploy/server/remote-deploy.sh`):
  1. Load the image.
  2. Back up all sites.
  3. Switch the image tag.
  4. Run migrations.
  5. Health-check every site.
  6. **Roll back to the previous image automatically** if migration or a health check fails.
  7. Keep the last 3 images.
- Staging deploys automatically after a release, if staging secrets exist. Production is
  deployed from Meer's laptop with `deploy/local-deploy.sh` (tag typed twice). Changed
  2026-11-20 after a security review: on a private repo on GitHub Free there are no
  environment secrets or approvals, so any production key in GitHub could be read by a
  workflow from any branch. Keeping it on the laptop costs nothing.
- Each server's deploy key is locked to `ssh-gate` (upload + deploy only); the deploy user
  has no docker access, and `compose.yaml` and `remote-deploy.sh` are root-owned and change
  only through `bootstrap.sh`.
- Secrets live only in GitHub Actions secrets and in a `chmod 600` config file on the
  server. Nothing secret is in git.

### 5. Development environment

The dev stack (`dev/compose.yaml`, `dev/scripts/*`) moves into this repository so it is
versioned with the code. A new laptop gets a working bench with `dev/scripts/bootstrap.sh`.

## Free-plan limits and how they are handled

| GitHub feature | Private repo on Free | What we do instead |
|---|---|---|
| Branch protection / rulesets | Not available | Local pre-push hook blocks direct pushes to `main`; CI on every PR; squash-merge only. Turn on rulesets if the repo goes public or to GitHub Pro. |
| Environments with approvals | Not available | Production deploys run from the laptop (`deploy/local-deploy.sh`); its key is never in GitHub. Staging is automatic. |
| Artifact attestations | Not available (Enterprise Cloud) | sha256 required by the server; released assets are never overwritten. Origin is not cryptographically proven. |
| CodeQL / secret scanning push protection | Not available (needs GHAS) | gitleaks (local + CI), bandit, Grype report. |
| GHCR private storage | 500 MB (image is larger) | Image tarball attached to the GitHub Release. |
| Actions minutes | 2,000 min/month | Caching; image build only on release or when `deploy/` changes; about 12 min per PR run. That is roughly 150 PR runs a month. |
| arm64 hosted runners | Public repos only | Images are amd64. An arm64 server (e.g. Oracle Ampere) builds the same Containerfile on the server (documented in `docs/DEVOPS.md`). |

**Making the repository public** would lift all of these limits for free: protection
rules, environments, CodeQL, GHCR, arm64 runners and unlimited minutes. The code holds no
secrets. This is a business decision for GIC.

## Consequences

- Each release is one tested, scanned and smoke-tested artifact; rollback means starting the
  previous image.
- Database migrations are forward-only. A failed deploy rolls the image back, but if a
  migration had already run, the database must be restored from the backup taken just before the deploy.
  The deploy log prints the backup path.
- Frappe/ERPNext upgrades are deliberate: change `deploy/versions.conf`, then CI and the smoke test prove it.
